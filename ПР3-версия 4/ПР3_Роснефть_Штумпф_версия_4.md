## 4.4. Sub-процесс 2B. Метрики скорости и data readiness

### Цель

Закрыть долг Сценария 33: руководители добычи и переработки требуют определить метрики скорости их направлений до следующего этапа унификации.

### Вход

- производственные данные добычи;
- данные переработки;
- MES / historian / LIMS / SCADA read-only;
- плановые показатели направлений;
- позиция CISO и производственных дирекций.

### Выход

- реестр метрик скорости добычи;
- реестр метрик скорости переработки;
- базовые значения или честный статус «не измерено»;
- план замера;
- data readiness report по 3 пилотным направлениям;
- протокол согласования с владельцами направлений.

### Ключевые метрики-кандидаты

| Направление | Метрика | Единица | Статус в ПР3 3.1 |
|---|---|---|---|
| Добыча | Выполнение плана добычи | % plan / млн т н.э. в месяц | Согласовать; baseline или «не измерено» |
| Добыча | Дебит / темп падения скважин | м³/сут или барр/сут | Согласовать как производственный ориентир |
| Добыча | Availability критичного оборудования | % | Не менять АСУ ТП без change control |
| Переработка | Глубина переработки | % | Использовать как контекст, не как обещанный эффект ИИ |
| Переработка | Выход светлых | % | Контекст для Г5 резерва |
| Переработка | Unplanned downtime | часы / % доступности | Критично для «Остановки без правил» |
| Переработка | Throughput vs plan | % | Для future ИИ-пилотов |
| Переработка | Энергозатраты / катализаторы / брак | $/т или % | Защитные метрики для Г5 |

### Правило

> Метрики скорости не дают прямой денежный эффект в ПР3. Они являются условием доверия, data readiness и будущего выхода Г5 из резерва.

## 4.5. Sub-процесс 2C. Бюджет унификации vs секвестр

### Проблема

Сценарий 33 требует сверить бюджет унификации 2–4 млрд ₽ с сокращением ИТ-расходов на четверть.

Если просто добавить унификацию как новые расходы, секвестр может стать формальным.

### Решение в ПР3 3.1

В waterfall нужно явно определить статус бюджета унификации.

| Вариант | Условие | Действие |
|---|---|---|
| A. Внутри protected costs | Бюджет унификации 2–4 млрд ₽ уже включён в protected / new recurring costs 3,5–7,5 млрд ₽ | Отдельно не вычитать; показать mapping, чтобы не было double count |
| B. Не включён | CFO / CDO не подтверждают, что унификация покрыта protected costs | Требуется additional freeze на 2,0–6,5 млрд ₽ или Board risk acceptance |
| C. Частично включён | Часть унификации в protected, часть — новый capex | Разделить строки; `unification_reconciliation_gap` должен быть ≤0 или формально принят |

### Метрика

```text
unification_reconciliation_gap =
approved_unification_budget
− earmarked_protected_or_freeze_source
```

Целевое значение:

```text
unification_reconciliation_gap ≤ 0
```

Если gap > 0, решение не принимается без:

- дополнительной заморозки некритичных проектов;
- или formal Board risk acceptance;
- или переноса части унификации на следующий период.

### Важно

Нельзя одновременно:

- считать protected costs 3,5–7,5 млрд ₽;
- отдельно вычитать унификацию 2–4 млрд ₽;
- и заявлять, что это разные расходы, если они не разведены в реестре.

## 4.6. Sub-процесс 2D. Freeze registry и business impact statement

### Требование Сценария 51

Финансовый директор требует перечень замороженных проектов с суммами.

### Обязательный артефакт

| Поле freeze registry | Описание |
|---|---|
| Project ID | Идентификатор проекта |
| Название | Краткое описание |
| Владелец | Бизнес-владелец и ИТ-владелец |
| Сумма | Годовой бюджет / capex / opex |
| NPV / payback | Экономическое обоснование |
| Strategic value | Почему проект важен или не важен |
| Business impact statement | Что теряется при заморозке |
| Risk of freeze | Операционный, коммерческий, ИБ, production risk |
| Owner of review | Кто пересматривает |
| Review date | Когда пересматривать |
| Unfreeze condition | При каком условии возвращается |
| Status | Frozen / reduced / cancelled / unfrozen |

### Правило

> 100% замороженных проектов должны иметь business impact statement, owner и review date. Иначе экономия не считается подтверждённой.

### Триггер

Если квартальная чистая экономия annualized <18,75 млрд ₽:

```text
additional_freeze_candidate_list = 2,0–6,5 млрд ₽
```

Но дополнительные проекты также должны проходить через freeze registry и BIS.

## 4.7. Sub-процесс 2E. Production change standard

### Требование «Остановка без правил»

Любое изменение производственного контура, АСУ ТП, MES, SCADA, historian, телеметрии КИИ не допускается без:

- RCA по предыдущим критичным инцидентам;
- change board;
- parallel run;
- rollback plan;
- подписи владельца производства;
- CISO approval для ИБ / КИИ;
- data contract для read-only телеметрии.

### Risk-based parallel run

| Тип изменения | Режим |
|---|---|
| АСУ ТП / SCADA / критичные производственные уставки | Строгий parallel run 30–90 дней, rollback, RCA |
| MES-интерфейсы, влияющие на производство | Поэтапно, пилотная установка, контрольная группа |
| Read-only телеметрия в ЕЦПК | Ускоренный режим при data contract, isolation, schema validation, security review |
| Коммерческие API канала | Canary / blue-green, не 30–90 дней по умолчанию |
| Отчётные витрины | T+1 или near real-time по SLA |

### Ключевое правило

> Нельзя одним правилом parallel run 30–90 дней замораживать и критичные производственные изменения, и некритичную read-only передачу данных.

## 4.8. Sub-процесс 2F. Buy / build / partner gate

### Требование Сценария 95

Покупка технологической компании не является обязательной, потому что белый лебедь №7 не назначен. Но процесс должен управлять опцией buy / build / partner.

### Gate

| Критерий | Порог | Если не выполнено |
|---|---|---|
| Технический due diligence | Продукт интегрируется в SAP / 1С / ЕЦПК / CRM | Buy отклоняется |
| Security due diligence | Нет критичных ИБ-рисков, данные изолируются, есть exit | Buy отклоняется |
| Legal due diligence | IP, contracts, compliance, data rights | Buy отклоняется |
| HR due diligence | Ключевые люди, retention ≥80% на 6 месяцев | Buy отклоняется |
| Architecture fit | Нет изолированного островка, API-first | Buy отклоняется |
| Integration cost | ≤2,0 млрд ₽ | Buy отклоняется или пересматривается |
| Seller response | ≤2 месяца | Если не успеваем — fallback |
| MVP / integration | 4–6 месяцев | Сравнить с fallback |
| Full integration | 12 месяцев | Не смешивать с seller response |

### Fallback readiness

Fallback должен быть готов до или параллельно с DD.

| Элемент fallback readiness | Требование |
|---|---|
| Контракт или RFQ | Есть коммерческое предложение |
| Security review | Прошёл ИБ-аудит |
| API-контракт | Определены интеграции с CRM / SAP / 1С / scoring |
| Data rights | Компания владеет данными и конфигурациями |
| Exit-план | Можно сменить подрядчика без потери процесса |
| MVP backlog | Минимальный функционал онбординга |
| Resource model | Есть люди или подряд, без зависимости от M&A |

### Цена автономии / vendor lock

Нужно измерять:

```text
dependency_score =
share_of_critical_functions_with_single_vendor
+ exit_cost
+ data_portability_risk
+ integration_lock_in
```

Если dependency_score высокий, buy или partner не признаются базовым сценарием без exit-плана.

## 4.9. Sub-процесс 2G. Governance и «Потолок доверия»

### Проблема

Лебедь №4 и Сценарий 33 показывают: решение никто не готов подписать.

### Решение

Приоритетный комитет должен вести decision log с полями:

| Поле decision log | Значение |
|---|---|
| Issue ID | Идентификатор вопроса |
| Question | Например: канал vs ЕЦПК; protected cut; additional freeze; buy / build / partner |
| Owner | Фамилия / роль |
| Options | Варианты |
| Price of each option | Деньги, срок, риск |
| Decision | Что выбрали |
| Risk acceptance | Кто принял риск |
| Deadline | Срок исполнения |
| Age | Сколько дней без решения |
| Escalation status | Эскалировано ли на Правление |

### Правила

| Правило | Порог |
|---|---|
| Критичное решение должно быть подписано | ≤5 рабочих дней |
| Если нет консенсуса | Эскалация на Правление |
| Если решение зависло | >10 рабочих дней — красная зона |
| Решение без owner | Не принимается |
| «Принято к сведению» без варианта и цены | Не считается решением |

# 6. Место агента в ПР3 3.1

Базовые ограничения агента из ПР3 3.0 сохраняются:

- агент не принимает финальное кредитное решение выше порога;
- агент не сокращает protected-сервисы;
- агент не меняет АСУ ТП / MES;
- агент не подписывает договоры;
- агент не обходит SAP / 1С / ЕЦПК;
- агент не получает доступ к производственному контуру без изоляции.

# 7. Эффект и trade-off с учётом Сценариев

## 7.1. Принцип учёта сценарных элементов

Сценарные долги не должны превращаться в красивые денежные эффекты.

| Элемент | Тип | Как учитывать |
|---|---|---|
| Метрики скорости добычи / переработки | Enabling / governance | Не денежный эффект; условие доверия и будущего Г5 |
| Бюджет унификации 2–4 млрд ₽ | Cost constraint | Либо внутри protected costs, либо additional freeze, либо Board risk acceptance |
| Freeze registry / BIS | Control | Не эффект; подтверждение экономии |
| Fallback readiness | Risk reduction / optional cost | Не базовый эффект; опциональная стоимость |
| DD gate | Option control | Не эффект; условие отказа / принятия buy |
| RCA / production change standard | Risk control | Не эффект; снижает риск остановки |
| Age of unresolved decisions | Governance control | Не эффект; снимает «потолок доверия» |

| Сценарный контроль | Что улучшаем | Что ухудшаем | Цена |

# 10. Итоговая формулировка ПР3 3.1

ПР3 версии 3.1 не заменяет ПР3 3.0, а усиливает её сценарной прослеживаемостью.

Сохранены главные лебединые решения:

1. **Лебедь №3** — быстрый B2B-онбординг возможен только как двухконтурный процесс с кредитными guardrails, мониторингом DSO и exception queue.
2. **Лебедь №4** — секвестр ИТ-бюджета возможен только с protected-фильтром, formal risk acceptance, явной поддержкой канала и risk-based parallel run.
3. **Белый №7 не назначен** — M&A остаётся опцией, а не базовым сценарием.

Добавлены явные сценарные механизмы:

1. **Сценарий 33** — согласование метрик скорости добычи и переработки, baseline или «не измерено», data readiness audit, сверка бюджета унификации 2–4 млрд ₽ с секвестром.
2. **Сценарий 51** — freeze registry с суммами, business impact statement, owner, review date; unfreeze control; fallback readiness; декомпозиция упущенной маржи.
3. **Сценарий 95** — build / buy / partner gate, DD checklist, retention, integration cost, разделение срока ответа продавцу и срока интеграции, цена автономии / vendor lock.
4. **«Остановка без правил»** — production change standard: RCA closure, change board, parallel run, rollback, подпись владельца производства.
5. **«Четверть без списка»** — protected-реестр и запрет базового сокращения SOC, КИИ, АСУ ТП, касс АЗС, канала и телеметрии без risk acceptance.
6. **«Потолок доверия»** — decision log, owner, age of unresolved critical decisions, эскалация на Правление при >10 рабочих дней.

Главный вывод:

> ПР3 3.1 проектирует не просто «улучшенные процессы», а управляемую систему, в которой каждый игровой долг — лебединый или сценарный — переведён в шаг процесса, обязательный артефакт, владельца, метрику проверки и trade-off. Без этого ПР3 оставалась бы сильной реакцией на лебедей, но не полной моделью управления изменениями для Роснефти в заданных условиях.
