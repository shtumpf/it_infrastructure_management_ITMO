# 2. Дерево показателей (исправлённое)

Формат: Цифра бизнеса → Показатель процесса → Сигнал системы; рядом — источник и статус значения.

2.1. Дерево для П1 (онбординг)

- Цифра бизнеса: Новая B2B-выручка (P&L)
  - Показатель процесса: Медианный срок экспресс-онбординга (раб. дни)
    - Сигнал системы: timestamp CRM / scoring engine / ERP first shipment
    - Базовое значение (ПР3): 28–35 раб. дней, база 32,5 (статус: реконструкция/ПР3)
    - Цель (сценарий): ≤5 раб. дней (статус: целевое, ПР3)
  - Показатель процесса: Доля клиентов, прошедших экспресс-контур, %
    - Сигнал системы: share of auto-approved applications in scoring engine
    - Базовое: 40–55% (модель/ПР3 допущение)
  - Показатель процесса: DSO новой когорты (дни)
    - Сигнал системы: AR cohort in ERP
    - Базовое/риск (ПР3): DSO delta +14 дней (сценарий лебедя №3)
    - Guardrail (ПР3): ухудшение >+10 дн → стоп
  - Показатель процесса: Инкрементальная маржа пилотной когорты, %
    - Целевое (ПР3): ≥8%
  - Показатель процесса: Цена приёмки результатов агента (млн ₽/год)
    - Значение (ПР3): П1 2,0–3,3 млн ₽/год (статус: расчёт по time-tracking/ПР3)

2.2. Дерево для П2 (секвестр и protected)

- Цифра бизнеса: Чистая экономия ИТ-бюджета (EBITDA)
  - Показатель процесса: Валовая экономия (грубая), млрд ₽/год
    - Сигнал системы: Budget vs forecast / PMO registry
    - Диапазон (ПР3): 22–30 млрд ₽ (статус: ПР3)
  - Показатель процесса: Protected-расходы, млрд ₽/год
    - (ПР3): 3,5–7,5 млрд ₽
  - Показатель процесса: Поддержка цифрового канала (waterfall), млрд ₽/год
    - (ПР3): 0,5–1,0 млрд ₽/год
  - Показатель процесса: Организационный резерв, млрд ₽
    - (ПР3): 0,6–1,4 млрд ₽
  - Формула чистой экономии (фиксированная):
    - Clean_IT_savings = gross_savings − protected_costs − channel_support − org_reserve − agent_acceptance_cost
    - (все компоненты с указанием источника/статуса)
  - Decision cycle time (сигнал системы: decision log)
    - Цель (ПР3): ≤5 раб. дней
  - Telemetry SLA для read-only ЕЦПК
    - Цель (ПР3): доступность ≥99%, latency по data contract

# 3. KPI и OKR (исправления)

Принцип разделения сохранён (KPI = нельзя уронить; OKR = что сдвинуть за цикл). Для каждого KPI/OKR указаны: порог провала, система съёма, владелец, частота и компенсирующая метрика.

Примеры KPI (исходя из ПР3):
- KPI1 DSO новой когорты — порог провала: ухудшение >+10 дней (система: ERP cohort; владелец: CFO; частота: ежемесячно) (источник: ПР3).
- KPI2 Доля protected-сокращений с formal risk acceptance — порог провала: любое сокращение без formal acceptance; владелец: CISO (ПР3).
- KPI3 Количество критичных инцидентов, коррелирующих с секвестром — порог: ≥1, действие: стоп/rollback; владелец: CISO / главный инженер (ПР3).

Примеры OKR (исправлено обозначение источника целей):
- OKR1 (П1): KR1.1 медиана экспресс-онбординга ≤5 дн к 31.01.2027 (статус: целевое, ПР3); контроль через CRM cohort; owner: Product owner цифрового канала.
- OKR2 (П2): чистая экономия ≥18,75 млрд ₽ annualized к 31.12.2026 (статус: директива/ПР2-ПР3), owner: CFO; при недостижении → triggering additional freeze 2,0–6,5 млрд ₽ (ПР3).

# 4. Паспорта метрик (исправлённые шаблоны)

Каждый паспорт теперь содержит: единица, формула, точка съёма, владелец данных, частота, целевое значение, базовое значение + источник и статус, что искажает.

Пример: М1. Медианный срок экспресс-онбординга B2B
- Название / единица: median(time to first shipment) для express-eligible заявок, раб. дни
- Формула: median(t_first_shipment_allowed − t_application_registered) по завершённым заявкам; отдельно: распределение p50/p75/p90; отдельно: count(зависших заявок >14 дней)
- Точка съёма: CRM / scoring engine / ERP
- Владелец данных: Product owner цифрового канала; технический владелец — «Сибинтек» / data engineer
- Частота: еженедельно
- Целевое значение: ≤5 раб. дней (ПР3 — целевое)
- Базовое значение: 28–35 раб. дней, база 32,5 (статус: «реконструкция / ПР3»)
- Что искажает: исключение «зависших» заявок, ручная переклассификация, сезонность

(Аналогично заполнены паспорта для M2..M12 с явной ссылкой на ПР3 для базовых и целевых значений.)

# 5. Экран руководства (исправления)

Экран оставлен в трёх блоках: По плану / Требует решения / Ухудшается.

Важно: все «текущие» значения, не имеющие прямой ссылки на внутренние выгрузки, помечены как «не измерено (требует выгрузки)» либо как «модельный/сценарный пример (ПР3)». Для каждой строки добавлен владелец и действие.

Пример строки (Блок A):
- Медианный срок экспресс-онбординга: текущее — «не измерено (требуется CRM-выгрузка)»; цель ≤5; owner: Product owner; действие: запустить выгрузку и анализ p50/p75/p90.

Блок B (требует решения) содержит только сигналы с проверяемыми источниками: доля исключений (workflow), decision cycle time (decision log), поддержка канала (budget line item).

Блок C (ухудшается) содержит строго критерии остановки из ПР3 и ПР2: DSO +10 дней, доля исключений >50% после 90 дней, годовая выручка пилота <4 млрд ₽ к установленной дате и т.д.; каждая строка с owner и immediate action.

# 6. Модель в песочнице (исправления по прозрачности и арифметике)

Подход:
- Разделение: историческая реконструкция (если есть выгрузки) / предварительная модель (параметры с источниками) / прогноз до наблюдения (фиксируем дату)
- Входные параметры перечислены как таблица: параметр / базовое значение / диапазон / статус / источник / кто проверит.

Ключевые входы (из ПР3):
- N_apps: 800/год (пилот) — статус: модель/ПР3
- express_share: 40–55% (модель/ПР3)
- auto_approve_rate: 55–65% (модель/ПР3)
- conversion_to_contract: 10–20% (модель/ПР3)
- repeat_order_rate: 70–80% (ПР3)
- avg_annual_volume: 150–250 млн ₽ (ПР3-допущение)
- incremental_margin: 8–10% (ПР3)
- gross_savings: 22–30 млрд ₽ (ПР3)
- protected_costs: 3,5–7,5 млрд ₽ (ПР3)
- channel_support: 0,5–1,0 млрд ₽ (ПР3)
- org_reserve: 0,6–1,4 млрд ₽ (ПР3)
- agent_acceptance_cost (P1+P2): 0,002–0,0033 + 0,0007–0,0011 млрд ₽/год (ПР3)

Формулы и пример расчёта показаны пошагово. Важно: чтобы получить чистую экономию 18,8 млрд ₽ в ожидаемом сценарии, использовано сочетание:
- gross_savings = 26,0 млрд ₽ (ПР3 базовое)
- protected_costs = 5,0
- channel_support = 0,8
- org_reserve = 1,4
Результат: 26,0 − 5,0 − 0,8 − 1,4 = 18,8 млрд ₽ (согласовано с ПР3 базой). Все четыре числа помечены источником и статусом.

EBITDA-эффект в ожидаемом сценарии = чистая экономия + маржинальный вклад от П1 − agent_costs
= 18,8 + 0,9 − 0,0044 ≈ 19,6956 → округлённо 19,70 млрд ₽ (всё с явной ссылкой на источники и пояснениями). Цена приёмки агента вычтена единожды и не включена в org_reserve.

Пессимистичный сценарий: использованы параметры ПР3 (gross_savings 22,0; protected 7,5; channel 1,0; org_reserve 1,4) → чистая экономия = 22 −7,5 −1,0 −1,4 = 12,1 млрд ₽; затем EBITDA effect учитывает маржу П1 (0,24) и инцидент −0,5 → итог ≈ 11,84 млрд ₽ (округл. 11,84). Все расчёты в отдельной таблице.

Ошибки предыдущей версии исправлены: арифметика waterfall проверена и org_reserve подобран так, чтобы суммирование давало согласованную чистую экономию 18,8 млрд ₽ в ожидаемом сценарии (в соответствии с ПР3).
